# RWKV7-G1j-1.5B training protocol validation

2026-10-18

This note records real-model training-path checks on the Transformers checkpoint `RWKV/RWKV7-G1j-1.5B-20260831`: local SFT, a worker-gradient aggregation canary, the initial WKV-state gradient path, and the first LoRA-SFT coordinator/worker prototype. The canary and State-Tuning checks are local; the distributed prototype status and limits are described in the final section.

## Model and environment

- Model: `RWKV/RWKV7-G1j-1.5B-20260831`, revision `2c18b29ab7fbece25ff6112281eea0fa41fcb30f`.
- Local checkpoint: `/workspace/RWKV7-G1j-1.5B-20260831`; `release-manifest.json` SHA-256 `e16c761b3991134756b4bdd6a6663a3d161ee9cce4cad484ebb7586cc5e2169c`.
- Manifest: 1,527,668,736 serialized BF16 parameters, 24 layers, hidden size 2,048, 32 heads × 64, vocabulary 65,536, training context 16,384.
- Runtime: RTX 3060 12 GiB; PyTorch 2.14.1+cu126, Transformers 5.20.1, TRL 1.16.0, PEFT 0.21.2, Datasets 5.1.0.
- Base parameters were BF16 and frozen; rank-8 attention LoRA factors were FP32. The 96 targets were `att.receptance`, `att.key`, `att.value`, and `att.output` across 24 layers (3,145,728 trainable parameters). No CPU/GPU layer offload or DeepSpeed was used. Safetensors may mmap files while loading; that is checkpoint I/O and did not offload training weights or activations to CPU.

The pinned model card documents the Transformers/TRL LoRA SFT route and the current chat template: [RWKV7-G1j-1.5B-20260831](https://huggingface.co/RWKV/RWKV7-G1j-1.5B-20260831).

## SFTTrainer path

`validate_g1j_sft_protocol.py` ran TRL `SFTTrainer` for two optimizer steps on four pinned conversational rows (`trl-lib/Capybara`, revision `e235e846458bff3398a88aed812347f7f0756520`, rows 1, 16, 21, and 25). It used assistant-only labels, no packing, max length 192, gradient checkpointing, BF16 base weights, and AdamW at `1e-4`.

Both optimizer steps completed. The final logged loss was 0.97894; all 192 LoRA tensors changed. Peak memory was 2.936 GiB allocated / 3.021 GiB reserved. The saved adapter reloaded on a fresh base and passed the stated output check (relative RMS logit delta 0.00458, cosine 0.999994, same top token). This is a short execution-path check, not a convergence or task-quality result.

TRL reports that the current template does not include the assistant end-of-turn token in the assistant loss mask. The user plans to revise the chat template later, so this run records that behavior and leaves the template unchanged. Re-run masking and SFT checks after the template changes.

## Long-context single-step profile

`profile_g1j_sft_context.py` ran one real BF16-base attention-LoRA forward/backward/AdamW step with gradient checkpointing and `use_cache=False`. To keep the large vocabulary projection limited to actual assistant target positions, the model's `logits_to_keep` path selected 28 assistant target positions. The long repeated prompt is therefore a recurrent-context and activation-capacity check with sparse labels; it is not a full-length TRL SFT admission for arbitrary assistant-label density.

| ---: | ---: | --- | ---: | ---: | ---: |
| 4,096 | 4,063 | Pass | 5.03 / 5.367 GiB | 6.236 GiB | 12.145 s |

Thus, this 12 GiB worker passed the 8k sparse-assistant-label profile, but not 16k. The 8k result is a useful capacity boundary, not a general production setting: real rows with more assistant target tokens can use more logits/loss memory, and must be measured with the final collator and template. No claim is made about sequence-length extrapolation quality.

## Worker-gradient and State-Tuning canaries

`validate_g1j_worker_and_state_protocol.py` compared two per-example loss-sum gradients, accumulated sequentially in one process, with the same examples run as a single padded batch. It is a local mathematical canary and **not two independent worker processes**.

- 48 assistant loss tokens; loss-sum relative error 0.000456.
- Gradient cosine 0.998621 and relative L2 error 0.05585, within the script's canary limits (cosine ≥ 0.99, relative L2 ≤ 0.1).
- The AdamW updates differed by up to 0.0002 in a parameter. The check therefore does not claim strict optimizer-update parity; batch-shape/BF16 numerical differences need follow-up before choosing exact coordinator update and accumulation semantics.

The same script froze the real 1.5B model and tested a rank-8 FP32 low-rank initial WKV state (`B`: 393,216 parameters / 1.5 MiB). With gradient checkpointing disabled, the chunked path produced finite nonzero state gradients and an AdamW step changed `B`. Against the eager path, loss relative error was 0.00966, gradient cosine 0.998644, and gradient relative L2 error 0.05613. This is one short sequence (`13` tokens, `6` labeled targets), not long-context State-Tuning admission or multiworker aggregation.

## Distributed implementation status

The first executable LoRA-SFT coordinator/worker slice now runs over authenticated HTTP. `g1j_dist_coordinator.py` serves an immutable adapter snapshot and pre-tokenized units, issues leases, renews/releases them, validates worker code/model/theta/unit hashes, checks gradient schema/finiteness/token counts, rejects stale and duplicate results, and applies one token-weighted AdamW update when the budget and minimum-unit count are met. `g1j_dist_worker.py` loads the frozen base once, computes one summed CE gradient per unit, and returns FP32 safetensors. The coordinator writes per-unit gradient payloads, an append-only event log, the resulting PEFT adapter, theta snapshot, optimizer state, and round metadata. `prepare_g1j_protocol_units.py` creates the pinned unit manifest.

An end-to-end round was split across two separate worker processes on the same RTX 3060, sequentially because the GPU cannot hold two 1.5B workers concurrently. Worker A returned two units (48 loss tokens), left the round open, and exited. Worker B joined later, received the remaining two units, and closed the round. The coordinator accepted all four units at one theta hash and applied one AdamW update over 190 loss tokens. The pre-update mean loss was 0.842687 and the theta hash changed from `cfeb5e8d41bcda3d5c48ca895c671532c1a56519514e6dddecbf7e2ea9375777` to `8ec095be70e923936b0d96f0b1d60c8650d616587f16975fc50206184597fe14`. The output adapter reloaded through `PeftModel` and matched all 192 coordinator theta tensors exactly; its probe logits and loss were finite.

That two-process run covered a single in-memory round, not production-ready federation. A graceful SIGINT/SIGTERM releases a worker's current lease immediately; an abrupt exit stops heartbeats and lets the lease expire for reissue (900 seconds by default, configurable at coordinator start). A worker that has submitted a result can leave without affecting the round. The run exercised one worker finishing its units and leaving before another joined; protocol unit tests cover graceful release and expiry requeue. Signal-driven release has not yet been fault-injected through the live HTTP worker. The current code supports a planned sequence of rounds, as described below. A restarted coordinator can continue from its last completed optimizer step with `--resume` (see below); it does not recover work that was in flight inside an interrupted round.

Workers now treat connection errors and coordinator 5xx responses as temporary: they keep retrying for at most three hours from the first detected outage, then exit cleanly. Heartbeats detect outages while a unit is running; a completed gradient is submitted after reconnection, or discarded and reacquired if its lease expired. Workers pin the coordinator `run_id` across reconnects and refuse to silently join a fresh run. Training completion is a separate coordinator flag: the earlier one-round CLI set it automatically when its token budget closed; current multi-step mode signals it after all planned steps close. `--manual-training-complete` requires an authenticated `POST /training-complete` after the final round. Workers poll that flag and exit only after receiving it. The retry deadline has fake-clock tests, and both automatic completion and the explicit HTTP completion signal passed short end-to-end smoke runs; a real three-hour outage has not been held open for testing.

The coordinator can explicitly materialize the pinned base from Hugging Face with `--fetch-model-from-hf`; it passes the unit manifest's repository and immutable revision to `snapshot_download`, then checks the downloaded `release-manifest.json` SHA-256 against the data manifest before serving workers. For this prototype the accepted repo/revision remain fixed to the G1j 1.5B validation target. The coordinator can also push saved adapter versions with `--push-adapter-to-hf --hf-adapter-repo <namespace/repo>`. Supply the write token only to the coordinator process via `HF_TOKEN` or `--hf-token`; the worker has no HF-token option and its Hub download explicitly disables authentication. Destination repositories are created private by default, and an existing public repo is rejected unless `--hf-adapter-public` explicitly opts into public upload. Each theta version is stored at `checkpoints/<run_id>/theta-<version>` with PEFT config/weights and provenance metadata, plus the AdamW state (`optimizer.safetensors`) when `--hf-push-optimizer` allows it (see Coordinator resume). By default `--hf-push-every-steps 10` queues every tenth optimizer update; the final adapter is queued even when the last version is not divisible by ten. Uploads run serially in a background queue so a worker's result response does not wait for Hub transfer. `/hub-push` (authenticated `POST`) retries failed versions and queues the current version; `coordinator_state.json` records status. After a restart with `--resume` the coordinator picks the queue back up (see Coordinator resume).

The protocol now treats each optimizer update as a step/round. `--epochs` repeats the manifest, while `--units-per-step` partitions each epoch; the default is one full epoch per step. A worker that first joins after the current step has issued any lease is queued. It is promoted only when the next step opens, at which point it receives that step's adapter snapshot. This membership boundary and the round-plan builder have unit tests. The earlier two-process real-model run exercised one step; a multi-step real-model HTTP run has not yet been performed.

```bash
/venv/main/bin/python g1j_dist_coordinator.py \
  --units runs/g1j_local_protocol/units.json \
  --model-id RWKV/RWKV7-G1j-1.5B-20260831 \
  --model-revision 2c18b29ab7fbece25ff6112281eea0fa41fcb30f \
  --model-dir /workspace/RWKV7-G1j-1.5B-20260831 \
  --fetch-model-from-hf \
  --push-adapter-to-hf \
  --hf-adapter-repo YOUR_HF_USERNAME/rwkv7-g1j-adapter
```

### Coordinator resume

Every completed optimizer step is committed to `<run-dir>/ckpt/theta-NNNNNN/` before the next round opens: the adapter (`theta.safetensors`), the AdamW moments and step counters (`optimizer.safetensors`, safetensors rather than a pickle), and a `state.json` with the run id, theta hash, planned step count, and the digests of the data manifest and round plan, plus base model, tokenizer and optimizer hyperparameters. A checkpoint is built under a temporary name, fsynced, and renamed into place, so a crash leaves either the previous version or a complete new one; `state.json` records a SHA-256 for each file. `--keep-checkpoints N` (default 3) keeps the newest N.

`--resume` loads the newest checkpoint under `--run-dir` whose files verify, falling back to an older one (with a warning) when the newest is damaged. It refuses a checkpoint whose data manifest, round plan, step count, base model, tokenizer or optimizer hyperparameters differ from this launch, and a run that has already finished. The run keeps its `run_id`, so running workers reconnect on their own: each loop re-joins, and a result computed under a pre-restart lease is refused as `unknown_lease` and dropped. Starting without `--resume` in a run directory that already holds checkpoints is an error, so an old run is never overwritten by accident. The optimizer step is exact: a resumed run reaches the same theta hash and moments as an uninterrupted run over the same unit schedule (tested with a small adapter).

Work in flight is not checkpointed. If the coordinator dies mid-round, that round restarts from its first unit, and gradients already received for it are discarded (they stay under `gradients/` but are not reused; on resume the interrupted round's folder is renamed `round-NNNNNN.discarded-<time>` so the old attempt is not mixed with the new one). This is deliberate and recovering in-flight work is not planned: the most a restart can cost is one round, so bound it with `--units-per-step`. The default of 0 puts a whole epoch in one round, so a crash can discard up to an epoch of computation; any positive value caps the loss at that many units. It is also a training setting, not only an operational one: it sets how many loss tokens each AdamW update averages and how many updates an epoch makes, so choose it for the optimization first. Smaller rounds also mean more checkpoints (each is about 36 MiB for the adapter plus moments, and the newest `--keep-checkpoints` are kept) and, with the default `--hf-push-every-steps 10`, a Hub push every ten of those smaller steps. A worker whose result arrives for a unit that was meanwhile re-credited to another worker now drops it instead of exiting (`duplicate_unit` joins `unknown_lease`, `expired_lease` and `round_closed` as a discarded result). Resume has been exercised by CPU tests against a real HTTP coordinator with synthetic gradients and a stubbed worker; it has not been run against the real 1.5B model on a GPU. Changing `rwkv_dist_protocol.py` or the worker files changes the worker-bundle hash, so restart the coordinator and all workers together after updating.

`--resume-from-hf` starts from a checkpoint pushed to the Hub instead, for a coordinator on a new machine: `--resume-from-hf --hf-adapter-repo USER/REPO --hf-run-id <run_id> [--hf-version N]` on a fresh `--run-dir` (a run directory that already holds checkpoints is refused; use `--resume` for that, and the two flags are mutually exclusive). Without `--hf-version` it takes the newest pushed version that verifies and reports the ones it skipped. Each push now records the resume metadata (run id, version, theta hash, planned steps, plan and data digests, base, tokenizer, optimizer hyperparameters), and a folder is used only if its adapter matches the recorded theta hash, its metadata names the run and version it was requested as, and the same compatibility checks as `--resume` pass; pushes made before this feature lack that metadata and are refused. The restored run keeps its `run_id` and commits its own local checkpoint, so later restarts use `--resume`.

`--hf-push-optimizer` decides whether a push carries the AdamW moments, which are what make the resumed trajectory identical to an uninterrupted one. The moments are derived from training gradients, so they are treated as more sensitive than the adapter itself. `auto` (default) uploads them only when the Hub reports the destination repository as private, and withholds them when it is public or its visibility is unknown. The decision follows the repository's actual visibility, not the `--hf-adapter-public` flag, because an existing private repo stays private whichever flag is given. `always` uploads them even to a public repository (the coordinator prints a warning at startup when combined with `--hf-adapter-public`), and `never` pushes the adapter only. Each push records `optimizer_included` and, when included, the file's SHA-256 in `adapter_metadata.json`, and `coordinator_state.json` records `optimizer_uploaded` per version. A checkpoint without moments still resumes the adapter, but the Adam moments restart cold, the coordinator says so, and the following steps then differ from an uninterrupted run (a test shows the hash diverges). Resuming from the Hub trusts whoever can write to that repository: the hashes detect damaged or partial uploads, not a deliberate substitution of the adapter and its metadata together, so resume only from a repository you control.

Hub push and resume are tested against a fake Hub that stores what `upload_folder` is given; the real `huggingface_hub` upload and download calls were not run against huggingface.co from this environment. With `--resume` and Hub pushing enabled, startup reconciles pushes with the Hub before serving: it lists the run's complete versions on the Hub and records them as uploaded, so a version already there is never pushed again (this also makes `POST /hub-push` idempotent); it re-queues each leftover entry in `hub_push_queue/` that still verifies and is not on the Hub; and it pushes the resumed version itself if that version falls on a push step and the Hub lacks it. A leftover entry is deleted when its adapter does not match its recorded hash, when it is newer than the version resumed from (a timeline that resume rolled back past, for example after falling back to an older checkpoint), or when it disagrees with the surviving local checkpoint for its version; an entry recorded for a different run id is left untouched and reported. If the Hub cannot be listed, startup continues and pending pushes are sent anyway, which at worst repeats an identical upload. If the Hub already holds versions newer than the one resumed from, the coordinator warns that reaching them again will overwrite those folders. The push history now stays in `coordinator_state.json` across later checkpoint writes (it used to be dropped each time a round closed).

`--keep-gradient-rounds N` bounds the disk used by the per-unit gradient files, each about 12 MiB (FP32 over 3,145,728 adapter parameters). They are now stored per round under `gradients/round-NNNNNN/`; after a round closes, folders of closed rounds beyond the newest N are deleted, and the open round's folder is never touched. The default, -1, keeps everything as before. Files from the earlier flat layout are left alone. The files are an audit record only: neither resume nor the Hub push reads them.

Remaining work includes timeout-based partial-step closure, speculative duplicate leases, independent concurrent workers, canary/audit and trust scores, validation rollback, worker signatures, and remote TLS deployment. The prototype sends the small token units directly through the coordinator. It binds to loopback by default and uses a bearer token over plain HTTP; do not expose it on a public interface. Remote workers need an authenticated TLS path before network rollout. The earlier numeric AdamW update discrepancy between different BF16 batch shapes still requires a defined coordinator/worker exactness tolerance; each step uses the selected per-unit summed-gradient aggregation contract directly.
