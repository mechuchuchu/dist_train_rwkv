# RWKV7-G1j-1.5B training protocol validation

2026-10-18

This note records real-model training-path checks on the Transformers checkpoint `RWKV/RWKV7-G1j-1.5B-20260831`: local SFT, a worker-gradient aggregation canary, the initial WKV-state gradient path, and the first LoRA-SFT coordinator/worker prototype. The canary and State-Tuning checks are local; the distributed prototype status and limits are described in the final section.

## Model and environment

- Model: `RWKV/RWKV7-G1j-1.5B-20260831`, revision `2c18b29ab7fbece25ff6112281eea0fa41fcb30f`.
- Local checkpoint: `/workspace/RWKV7-G1j-1.5B-20260831`; `release-manifest.json` SHA-256 `e16c761b3991134756b4bdd6a6663a3d161ee9cce4cad484ebb7586cc5e2169c`.
- Manifest: 1,527,668,736 serialized BF16 parameters, 24 layers, hidden size 2,048, 32 heads × 64, vocabulary 65,536, training context 16,384.
- Runtime: RTX 3060 12 GiB; PyTorch 2.14.1+cu126, Transformers 5.20.1, TRL 1.16.0, PEFT 0.21.2, Datasets 5.1.0.
- Base parameters were BF16 and frozen; rank-8 attention LoRA factors were FP32. The 96 targets were `att.receptance`, `att.key`, `att.value`, and `att.output` across 24 layers (3,145,728 trainable parameters). No CPU/GPU layer offload or DeepSpeed was used. Safetensors may mmap files while loading; that is checkpoint I/O and did not offload training weights or activations to CPU.

The pinned model card documents the Transformers/TRL LoRA SFT route and the current chat template: [RWKV7-G1j-1.5B-20260831](https://huggingface.co/RWKV/RWKV7-G1j-1.5B-20260831).

## SFTTrainer path

`validate_g1j_sft_protocol.py` ran TRL `SFTTrainer` for two optimizer steps on four pinned conversational rows (`trl-lib/Capybara`, revision `e235e846458bff3398a88aed812347f7f0756520`, rows 1, 16, 21, and 25). It used assistant-only labels, no packing, max length 192, gradient checkpointing, BF16 base weights, and AdamW at `1e-4`.

Both optimizer steps completed. The final logged loss was 0.97894; all 192 LoRA tensors changed. Peak memory was 2.936 GiB allocated / 3.021 GiB reserved. The saved adapter reloaded on a fresh base and passed the stated output check (relative RMS logit delta 0.00458, cosine 0.999994, same top token). This is a short execution-path check, not a convergence or task-quality result.

TRL reports that the current template does not include the assistant end-of-turn token in the assistant loss mask. The user plans to revise the chat template later, so this run records that behavior and leaves the template unchanged. Re-run masking and SFT checks after the template changes.

## Long-context single-step profile

`profile_g1j_sft_context.py` ran one real BF16-base attention-LoRA forward/backward/AdamW step with gradient checkpointing and `use_cache=False`. To keep the large vocabulary projection limited to actual assistant target positions, the model's `logits_to_keep` path selected 28 assistant target positions. The long repeated prompt is therefore a recurrent-context and activation-capacity check with sparse labels; it is not a full-length TRL SFT admission for arbitrary assistant-label density.

| Requested context | Actual tokens | Step | Peak allocated / reserved | Free VRAM after | Step time |
| ---: | ---: | --- | ---: | ---: | ---: |
| 4,096 | 4,063 | Pass | 5.03 / 5.367 GiB | 6.236 GiB | 12.145 s |
| 8,192 | 8,191 | Pass | 7.174 / 7.832 GiB | 3.773 GiB | 33.369 s |
| 16,384 | 16,351 | OOM during the step | 11.462 / 11.586 GiB observed | 0.646 GiB after cleanup | — |

Thus, this 12 GiB worker passed the 8k sparse-assistant-label profile, but not 16k. The 8k result is a useful capacity boundary, not a general production setting: real rows with more assistant target tokens can use more logits/loss memory, and must be measured with the final collator and template. No claim is made about sequence-length extrapolation quality.

## Worker-gradient and State-Tuning canaries

`validate_g1j_worker_and_state_protocol.py` compared two per-example loss-sum gradients, accumulated sequentially in one process, with the same examples run as a single padded batch. It is a local mathematical canary and **not two independent worker processes**.

- 48 assistant loss tokens; loss-sum relative error 0.000456.
- Gradient cosine 0.998621 and relative L2 error 0.05585, within the script's canary limits (cosine ≥ 0.99, relative L2 ≤ 0.1).
- The AdamW updates differed by up to 0.0002 in a parameter. The check therefore does not claim strict optimizer-update parity; batch-shape/BF16 numerical differences need follow-up before choosing exact coordinator update and accumulation semantics.

The same script froze the real 1.5B model and tested a rank-8 FP32 low-rank initial WKV state (`B`: 393,216 parameters / 1.5 MiB). With gradient checkpointing disabled, the chunked path produced finite nonzero state gradients and an AdamW step changed `B`. Against the eager path, loss relative error was 0.00966, gradient cosine 0.998644, and gradient relative L2 error 0.05613. This is one short sequence (`13` tokens, `6` labeled targets), not long-context State-Tuning admission or multiworker aggregation.

## Distributed implementation status

The first executable LoRA-SFT coordinator/worker slice now runs over authenticated HTTP. `g1j_dist_coordinator.py` serves an immutable adapter snapshot and pre-tokenized units, issues leases, renews/releases them, validates worker code/model/theta/unit hashes, checks gradient schema/finiteness/token counts, rejects stale and duplicate results, and applies one token-weighted AdamW update when the budget and minimum-unit count are met. `g1j_dist_worker.py` loads the frozen base once, computes one summed CE gradient per unit, and returns FP32 safetensors. The coordinator writes per-unit gradient payloads, an append-only event log, the resulting PEFT adapter, theta snapshot, optimizer state, and round metadata. `prepare_g1j_protocol_units.py` creates the pinned unit manifest.

An end-to-end round was split across two separate worker processes on the same RTX 3060, sequentially because the GPU cannot hold two 1.5B workers concurrently. Worker A returned two units (48 loss tokens), left the round open, and exited. Worker B joined later, received the remaining two units, and closed the round. The coordinator accepted all four units at one theta hash and applied one AdamW update over 190 loss tokens. The pre-update mean loss was 0.842687 and the theta hash changed from `cfeb5e8d41bcda3d5c48ca895c671532c1a56519514e6dddecbf7e2ea9375777` to `8ec095be70e923936b0d96f0b1d60c8650d616587f16975fc50206184597fe14`. The output adapter reloaded through `PeftModel` and matched all 192 coordinator theta tensors exactly; its probe logits and loss were finite.

This is a single in-memory round, not production-ready federation. A worker joining during an open round receives the current theta snapshot and leases pending work. A graceful SIGINT/SIGTERM releases its current lease immediately; an abrupt exit stops heartbeats and lets the lease expire for reissue (900 seconds by default, configurable at coordinator start). A worker that has submitted a result can leave without affecting the round. The two-process run exercised a worker finishing its units and leaving before another joined; protocol unit tests cover graceful release and expiry requeue. Signal-driven release has not yet been fault-injected through the live HTTP worker.

Workers now treat connection errors and coordinator 5xx responses as temporary: they keep retrying for at most three hours from the first detected outage, then exit cleanly. Heartbeats detect outages while a unit is running; a completed gradient is submitted after reconnection, or discarded and reacquired if its lease expired. Workers pin the coordinator `run_id` across reconnects and refuse to silently join a fresh run. Training completion is a separate coordinator flag: this one-round CLI sets it automatically when its full token budget closes, while `--manual-training-complete` requires an authenticated `POST /training-complete` after the actual final round. Workers poll that flag and exit only after receiving it. The retry deadline has fake-clock tests, and both automatic completion and the explicit HTTP completion signal passed short end-to-end smoke runs; a real three-hour outage has not been held open for testing.

The coordinator can explicitly materialize the pinned base from Hugging Face with `--fetch-model-from-hf`; it passes the unit manifest's repository and immutable revision to `snapshot_download`, then checks the downloaded `release-manifest.json` SHA-256 against the data manifest before serving workers. For this prototype the accepted repo/revision remain fixed to the G1j 1.5B validation target. The coordinator can also push saved adapter versions with `--push-adapter-to-hf --hf-adapter-repo <namespace/repo>`. Supply the write token only to the coordinator process via `HF_TOKEN` or `--hf-token`; the worker has no HF-token option and its Hub download explicitly disables authentication, so the coordinator's credential is not shared. Destination repositories are created private by default, and an existing public repo is rejected unless `--hf-adapter-public` explicitly opts into public upload. Each theta version is stored at `checkpoints/<run_id>/theta-<version>` with PEFT config/weights and provenance metadata only. Upload runs in a background thread so a worker's result response does not wait for Hub transfer. The current protocol has a single optimizer update, so one run produces one updated adapter snapshot; `/hub-push` (authenticated `POST`) retries a failed upload. The local `coordinator_state.json` records upload status.

```bash
/venv/main/bin/python g1j_dist_coordinator.py \
  --units runs/g1j_local_protocol/units.json \
  --model-id RWKV/RWKV7-G1j-1.5B-20260831 \
  --model-revision 2c18b29ab7fbece25ff6112281eea0fa41fcb30f \
  --model-dir /workspace/RWKV7-G1j-1.5B-20260831 \
  --fetch-model-from-hf \
  --push-adapter-to-hf \
  --hf-adapter-repo YOUR_HF_USERNAME/rwkv7-g1j-adapter
```

Remaining work includes durable coordinator recovery/resume from a mid-round crash, timeout-based partial-round closure, speculative duplicate leases, multi-round training, independent concurrent workers, canary/audit and trust scores, validation rollback, worker signatures, and remote TLS deployment. The prototype sends the small token units directly through the coordinator. It binds to loopback by default and uses a bearer token over plain HTTP; do not expose it on a public interface. Remote workers need an authenticated TLS path before network rollout. The earlier numeric AdamW update discrepancy between different BF16 batch shapes still requires a defined coordinator/worker exactness tolerance; this round uses the selected per-unit summed-gradient aggregation contract directly.
