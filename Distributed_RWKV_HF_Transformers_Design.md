# RWKV-7 HF Transformers adaptation: state tuning, QLoRA, and offload

2026-10-18

This note adapts the coordinator/worker plans in [`Distributed_RWKV_State_Tuning_Design.md`](Distributed_RWKV_State_Tuning_Design.md) and [`Distributed_RWKV_LoRA_SFT_Design.md`](Distributed_RWKV_LoRA_SFT_Design.md) to the local Hugging Face Transformers release [`/workspace/RWKV7-G1k-13.3B-20260930`](../RWKV7-G1k-13.3B-20260930). The existing plans describe the `train_temp` CUDA path; this model instead exposes a Transformers `Rwkv7ForCausalLM` with Python/PyTorch RWKV operators and a custom recurrent cache. Keep the coordinator protocol, immutable base identity, token-weighted summed-gradient contract, audit, canary, and rollback. Replace the model-loading, adapter injection, cache, and offload assumptions as described here.

## 1. Local checkpoint and runtime

The local release manifest records 13,270,298,624 BF16 parameters in 2,019 tensors. Its configuration is 61 layers, hidden width 4,096, 64 heads × 64, vocabulary 65,536, and training context 25,600. The release-manifest SHA-256 is `9c70be77c4ab6f051da996c6c6adcbb02fcd49fa6550ad32fe7b7403214a4fe3`; the safetensors index SHA-256 is `9daff37c8093938c28d8c8cf5ce2b02381073f4de514708c6ce38ec06db5f501`. Pin these identities (and preferably the manifest's per-file shard hashes) in every worker job.

The tested environment is `/venv/main`: PyTorch 2.14.1+cu126, Transformers 5.20.1, Accelerate 1.15.0, bitsandbytes 0.50.2, PEFT 0.21.2, and DeepSpeed 0.19.7. The GPU is an RTX 3060 with 12 GiB. `bitsandbytes` is installed in the active environment; the quantized model is currently constructed at load time and no second, serialized quantized checkpoint was written.

Hardware selection is VRAM-tiered in [`VRAM_Baseline_2026-10-18.md`](VRAM_Baseline_2026-10-18.md). For this 13.3B checkpoint, short-context NF4 QLoRA is already measured on 12 GiB; BF16 LoRA and State Tuning use an 80GB-class GPU (H100 as the primary reference) as the design target. A 48GB GPU is a lower-tier BF16 candidate pending admission. H100 is therefore the reference for the higher-memory recipe, not a blanket requirement for every 13.3B task. All VRAM tiers are per worker; this protocol does not currently combine multiple GPUs inside one worker.

## 2. NF4 quantization and measured placement

Use NF4 with double quantization for the frozen linear layers. Keep the vocabulary embedding, output head, norms, and other non-`Linear` tensors in the model compute dtype. This is the QLoRA-friendly recipe documented by [Transformers bitsandbytes integration](https://huggingface.co/docs/transformers/quantization/bitsandbytes). The HF implementation routes the block projections through ordinary `nn.Linear` calls, so bitsandbytes replaces them without the `train_temp` Cmix adapter-kernel rewrite.

All probes in this section are inference-only: synthetic prefill followed by one recurrent decode token, with no loss, backward pass, or optimizer step. Logits remained finite. Full GPU placement quantized all 366 block linears and kept the head and embeddings BF16. At 12 tokens it used 7.56 GiB model footprint, peaked at 7.87 GiB allocated / 8.45 GiB reserved, and completed prefill plus decode in 1.12 seconds. Long prompts passed at 4,096 tokens (10.15 GiB peak allocated, 8.34 seconds) and 5,120 tokens (10.72 GiB, 10.12 seconds). A 6,144-token run failed during recurrent-state update with only a few MiB free; 8,192 failed in the WKV intermediate allocation. The reports for the successful long runs are [`hf_rwkv7_nf4_all_gpu_t4096_20261018.json`](hf_rwkv7_nf4_all_gpu_t4096_20261018.json) and [`hf_rwkv7_nf4_all_gpu_t5120_20261018.json`](hf_rwkv7_nf4_all_gpu_t5120_20261018.json). These are capacity probes, not quality or long-context accuracy evaluations.

Mixed placement kept embeddings, head, and the first 40 blocks on CUDA, with 21 blocks and `ln_out` on CPU. It quantized the 240 CUDA block linears; CPU-offloaded linears stayed ordinary FP32, giving a 23.19 GiB model footprint and about 17.3–17.8 GiB process RSS. The 12-token probe peaked at 7.34 GiB allocated / 8.05 GiB reserved and took 15.01 seconds. This placement passed at 64, 1,024, 4,096, and 6,144 prompt tokens; the 6,144-token prefill plus decode took 49.32 seconds and peaked at 10.86 GiB allocated / 11.22 GiB reserved. The 8,192-token run failed in a WKV intermediate allocation. During the successful 6,144 run, host available RAM was 204.96 GiB and cgroup usage was 42.58 / 76.43 GiB; the process RSS after forward was 17.35 GiB. Reports: [`hf_rwkv7_nf4_offload_t6144_20261018.json`](hf_rwkv7_nf4_offload_t6144_20261018.json), plus the 64/1,024/4,096-token reports in the same directory. The runner must allocate each layer's WKV cache on that block's device: Accelerate hooks do not split this model's custom `Rwkv7Cache` object. The tested runner contains that cache placement patch; see [`profile_hf_rwkv7_nf4_offload.py`](profile_hf_rwkv7_nf4_offload.py).

For this 12 GiB card, keep the full NF4 model on GPU for short requests. CPU layer offload works as a capacity fallback and increased the tested long-prompt ceiling from 5,120 to 6,144 tokens, while the short request was about 13× slower and the 6,144-token prefill took 49 seconds. The mixed map used FP32 inputs/compute to keep the CPU layers compatible; it is an inference probe, not a training placement recipe. Hugging Face documents `device_map="auto"` as an inference dispatch path, so do not use it as the distributed training strategy. Changing WKV chunk size from 64 to 16 did not make the 8,192-token mixed run fit.

## 3. QLoRA SFT on the HF module tree

The block contains six accessible linear projections: `att.receptance`, `att.key`, `att.value`, `att.output`, `ffn.key`, and `ffn.value`. For the existing attention-only v1, match the exact suffixes `att.receptance`, `att.key`, `att.value`, and `att.output`. A generic target list of `key` and `value` also selects the two FFN projections; avoid that accidental expansion. Unlike the `train_temp` fused Cmix path described by the original LoRA draft, this HF path calls the FFN linears as modules, so an all-six-projection experiment is possible later without first extending a custom CUDA kernel. Keep it as a separately profiled target recipe.

The tested recipe is NF4 + double quantization, BF16 quantized-linear compute, PEFT rank 8 / alpha 16 / dropout 0, gradient checkpointing, and FP32 adapter factors. An actual 16-token synthetic causal-LM step selected exactly 244 attention linears (`61 × 4`), created 15,990,784 trainable parameters, produced finite gradients for all 488 adapter tensors, and completed an AdamW step. Loss was 13.6821, global gradient norm 11.7324, and step time 3.09 seconds after load. Peak was 10.14 GiB allocated / 10.57 GiB reserved, leaving 0.93 GiB free. The reproducible runner and report are [`profile_hf_rwkv7_qlora_step.py`](profile_hf_rwkv7_qlora_step.py) and [`hf_rwkv7_nf4_qlora_step_20261018.json`](hf_rwkv7_nf4_qlora_step_20261018.json).

The standard `prepare_model_for_kbit_training` path upcasts non-quantized BF16 parameters, including embedding/head, to FP32. It passed at 16 tokens but OOMed during backward at 1,024. A second tested route freezes the base in its original BF16 dtype, adds the FP32 adapters, and enables input gradients/checkpointing without that upcast; it passed full backward and AdamW steps at 16, 1,024, and 2,048 tokens. At 2,048 it peaked at 10.91 GiB allocated / 11.36 GiB reserved with only 0.24 GiB free; 2,560 OOMed. The 1,024-token preserved-base run peaked at 9.39 GiB allocated / 9.92 GiB reserved and left 1.68 GiB free. See `hf_rwkv7_nf4_qlora_step_t1024_bf16base_20261018.json`, `hf_rwkv7_nf4_qlora_step_t2048_bf16base_20261018.json`, and `hf_rwkv7_nf4_qlora_step_t16_bf16base_20261018.json`. For real SFT start at micro-batch 1 and no more than 1,024 tokens, use assistant-only labels, and measure a full step before increasing context. The 2,048 result is a boundary probe with too little safety margin for a routine run. Keep `use_cache=False` for ordinary QLoRA training and do not wrap the forward in `torch.no_grad()`.

The model's native `w1/w2`, `a1/a2`, `v1/v2`, and `g1/g2` RWKV factors are part of the frozen checkpoint, not PEFT LoRA modules. Keep them frozen in this recipe. Add special-token embedding/head rows only through the explicit split-row path in the original LoRA design; `modules_to_save` on the complete vocabulary matrices would unfreeze/save far too much state.

## 4. State Tuning through `Rwkv7Cache`

The HF implementation includes a differentiable PyTorch WKV reference/chunked path and a `Rwkv7Cache` whose WKV slot is FP32. `Rwkv7Cache.write()` rebinds recurrent slots when gradients are enabled and a state requires gradients, preserving the graph instead of overwriting it in place. A tiny two-layer, 64-hidden, 16-token CPU probe produced finite loss and finite gradients for FP32 initial WKV states. This establishes a small reference path without extending `train_temp`'s custom CUDA autograd kernel; it does not yet establish 13.3B throughput or memory admission.

For the HF state-tuning worker, freeze the base model, form each layer's `S0[l,h] = A[l,h] @ B[l,h]` in FP32, allocate an `Rwkv7Cache`, place `S0` into each layer's WKV slot, and pass that cache to the normal model forward. Keep the two token-shift slots at zero for v1. Every independent SFT row starts from the same learned initial state; do not carry the ending state into a different row or worker unit. Retain the original design's low-rank rank-8 basis, state/token-row gradient payload, and coordinator-only optimizer unless experiments justify changing them.

Do not enable gradient checkpointing in the first state-gradient reference. This model mutates recurrent cache across blocks; its source warns that checkpoint replay with a live state can read an already-advanced state and produce incorrect gradients. Run an uncheckpointed short sequence with `use_cache=False` and an explicitly supplied differentiable cache, then compare loss and every `B` gradient with the same tiny model using `wkv_implementation="eager"` (or a direct tokenwise WKV reference). Add checkpointing only after a replay-safe implementation has its own parity test. Also test `B=1`, duplicated batch rows, and packed independent rows to ensure gradients sum to the shared initial-state parameter correctly.

The quantized QLoRA smoke test above does not exercise `dS0`; NF4 state-tuning remains a separate backend admission. First compare BF16-base state gradients against the HF reference, then test NF4 backward and FP32 state-gradient invariants. Do not infer state-tuning VRAM or correctness from the LoRA step.

## 5. Offload and DeepSpeed decision

The custom mixed CPU/GPU device map is validated for inference only. Its 17.3–17.8 GiB RSS and 42.6 GiB cgroup usage are inference measurements; do not use them as training RAM figures. It has model-specific cache placement and FP32 CPU modules; it should not be reused as a `Trainer` or PEFT training map.

An attempted 16-token QLoRA backward with the same CPU/GPU `device_map` failed: `MmBackward0` expected a parameter on `meta` but received a CUDA gradient. The base layers were dispatched through inference offload hooks and all LoRA tensors landed on CUDA, so no optimizer step completed. This is recorded in [`hf_rwkv7_nf4_qlora_offload_step_t16_20261018.json`](hf_rwkv7_nf4_qlora_offload_step_t16_20261018.json); it is a failed compatibility probe, not a training result. The runner is [`profile_hf_rwkv7_nf4_qlora_offload_step.py`](profile_hf_rwkv7_nf4_qlora_offload_step.py).

The local model is in safetensors format. This workspace path did not disable mmap, so Transformers read the shards through `safe_open` with mmap during checkpoint loading. That is file-loading I/O. The tested inference map dispatches CPU-layer FP32 weights through Accelerate's inference hooks. Mmap loading does not offload training activations or make the inference `device_map` safe for backward.

DeepSpeed 0.19.7 is installed, but no DeepSpeed training/offload run has been completed. The rank-8 attention-only adapter has about 61 MiB of FP32 weights, so optimizer-only offload is unlikely to move the context limit materially. A separate DeepSpeed ZeRO-3 CPU-parameter-offload run remains the next training-offload test, initially with a BF16 base; NF4 modules, ZeRO-3 partitioning, and this model's recurrent gradients are not validated together. Transformers documents ZeRO-3 parameter and optimizer offload in its [DeepSpeed integration guide](https://huggingface.co/docs/transformers/deepspeed). Do not infer training offload behavior from the inference map or combine these features until a full backward, optimizer step, gradient check, and memory profile pass.

## 6. Next admission sequence

1. Save a BF16-base attention-only PEFT adapter, reload it, and compare logits/adapter outputs with the in-memory adapter.
2. Measure real masked SFT forward/backward/AdamW steps at `B=1` with contexts up to 1,024 first, recording peak VRAM, host RSS, throughput, loss, and gradient finiteness. The 2,048-token result is too close to the 12 GiB limit for routine use, and 2,560 OOMed.
3. Implement the HF `Rwkv7Cache` initial-state injection and compare tiny-model `B` gradients to the explicit WKV reference; only then profile the 13.3B base.
4. Compare BF16 and NF4 gradients on identical batches. Add special-token rows and held-out quality checks after the adapter-only path is stable.
5. Training CPU offload remains unverified. Test DeepSpeed ZeRO-3 CPU parameter offload as a separate BF16-base QLoRA recipe, recording a real backward and optimizer step, gradient finiteness, GPU peak, process RSS, and cgroup use. Treat the inference-only 6,144-token result as unrelated to the training context limit. Keep NF4+ZeRO-3 and state tuning as separate follow-up admissions.
